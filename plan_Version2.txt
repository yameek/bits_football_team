Football Team Treasury & Session Management Web App
Software Requirements Specification (SRS) and Flow Diagrams
Version: 1.0
Owner: Treasurer
Prepared for: Team and Management


1. Overview
1.1 Purpose
This web application supports a football team’s treasurer in:
- Booking fields for practice or matches
- Managing upcoming sessions
- Collecting monthly contributions
- Recording attendance per session
- Automatically calculating and deducting per-session fees from present members only
- Handling on-field collections for guests/new members
- Tracking team-level and individual balances
- Sharing financial and session status with team and management

1.2 Goals and Key Outcomes
- Eliminate manual calculations and errors for per-session fee distribution
- Provide transparent balances for members and management
- Streamline on-field and online payments and logging
- Maintain a reliable audit trail and reports

1.3 In-Scope
- Session scheduling and field booking info storage
- Attendance tracking and per-session fee allocation/deduction
- Monthly contributions and on-field collections
- Member balances and team aggregate balance
- Transaction history and exportable reports
- Role-based access (Treasurer, Manager, Member, Admin)
- Basic notifications (email/SMS optional) and shareable dashboards
- Secure authentication and authorization

1.4 Out-of-Scope (v1)
- Online payment gateway integration (can be added later)
- Multi-currency, taxes
- Complex accounting (depreciation, liabilities, accruals)
- Inventory management for equipment


2. Stakeholders and Roles
2.1 Stakeholders
- Treasurer: Manages finances, sessions, attendance, and payments
- Manager/Coach: Schedules sessions, views status
- Members/Players: View balance, attendance, pay contributions
- Management: Read-only access to financial summaries and reports
- System Admin: Config and maintenance

2.2 Roles & Permissions
- Admin: Full access (manage users, configurations, all data)
- Treasurer: Full finance, sessions, attendance, field info; share dashboards; exports
- Manager: Create sessions, fields; mark attendance; read financial summaries
- Member: View own balance, attendance, statements; pay contributions
- Viewer (Management): Read-only dashboards/reports

Access control: Role-based; enforce at API and UI route levels.


3. Definitions and Glossary
- Session: A scheduled practice or match at a field with costs
- Attendance: Record of member present/absent for a session
- Contribution: Monthly member payment that increases member balance
- Session fee: Total session cost allocated equally among present members
- On-field collection: Immediate payment from attendee (member or guest) at session time
- Balance: Member’s running balance (credit positive, debit negative or vice versa per design)
- Team balance: Sum of all member balances (and optionally treasury cash ledger)

FR-10 Record on-field collections and apply to session fees

FR-20 Mobile-responsive UI for on-field usage

Business Rules
BR-01 Per-head session fee = round(total_session_cost / headcount_present, 2).
BR-02 Rounding residual must be handled either via a team-level rounding adjustment transaction or distributed +$0.01 to first N attendees to match exact total.
BR-03 Only present attendees are charged; absent members are not charged.
BR-04 Monthly contribution increases member balance and is not tied to any specific session.
BR-05 On insufficient balance, allow recording a due and later reconciliation via contribution/on-field collection.
BR-06 On-field collection can be logged as a positive transaction that immediately offsets the session fee.
BR-07 Attendance (member_id, session_id) must be unique.
BR-08 A transaction must never be deleted; use soft-delete if needed and maintain an audit trail.
BR-09 Team balance is the sum of all member balances. If a separate treasury cash ledger is kept, present both views clearly.
BR-10 Guest attendee handling: allow “guest” entity or ad-hoc attendee name; fees collected on-field do not affect member balances unless the guest is promoted to member.

7. Core Algorithms
7.1 Per-Session Fee Calculation
- total_cost = field_cost + transport_cost + drinks_cost + emergency_fund
- present_count = count(attendance where present = true)
- If present_count = 0: no charges; stop
- raw_fee = total_cost / present_count
- per_head_fee = round(raw_fee, 2)
- rounding_diff = total_cost - (per_head_fee * present_count)
- If rounding_diff != 0:
  - Option A: Create one team-level 'adjustment' transaction for rounding_diff
  - Option B: Distribute 0.01 adjustments across first |rounding_diff * 100| attendees

7.2 Auto-Deduction Workflow
- For each present attendee:
  - if member.balance >= per_head_fee:
      - create transaction(session_fee, -per_head_fee, method=balance)
      - update member.balance -= per_head_fee
      - attendance.paid_amount = per_head_fee; paid_flag = true; payment_method=balance
  - else:
      - due = per_head_fee - member.balance (if positive)
      - if member.balance > 0:
          - transaction(session_fee, -member.balance)
          - attendance.paid_amount += member.balance
          - member.balance = 0
      - mark paid_flag=false; payment_method='mixed' or null
      - allow on-field collection or later contribution
- On on-field collection:
  - transaction(onfield_payment, +collected_amount, method=cash/mobile)
  - Apply to unpaid attendance of that session first; set paid_flag when paid_amount >= charged_amount
  - Optionally also mirror as session_fee negative transaction if you want strict double-entry per session

7.3 Monthly Contribution
- transaction(contribution, +amount)
- update member.balance += amount

7.4 Team Balance
- team_balance = SUM(member.balance)
- If tracking treasury cash box separately, maintain separate ledger and show both metrics.

14. Acceptance Criteria (Samples)
AC-01 Creating a session:
- Given valid field, date, and costs, when the treasurer saves, then the session appears on calendar and status=planned.

AC-02 Finalizing a session with attendance:
- Given attendance marked for at least one member present, when treasurer finalizes, then per-head fee is computed, transactions created (session_fee), balances updated, and attendance records show paid or due.

AC-03 Absent members not charged:
- Given a member marked absent, when session finalizes, then no session_fee transaction is created for that member and their balance remains unchanged.

AC-04 Monthly contribution:
- Given a contribution recorded, then the member balance increases and a transaction of type 'contribution' is logged.

AC-05 On-field collection for insufficient balance:
- Given a member with unpaid session fee, when on-field collection is recorded, then an onfield_payment transaction is created, the unpaid attendance is reconciled, and paid_flag becomes true when fully covered.

AC-06 Team balance:
- Given multiple member balances, then the team balance equals the sum of member balances within 1 cent of rounding policy.

AC-07 Exports:
- Given a date range, when treasurer exports transactions, then a CSV file is downloaded with all matching records.

16. Edge Cases and Handling
- No attendees present: Do not finalize fees; warn and keep session planned or mark canceled
- Late attendees toggled after finalize: Require re-finalize with warning (may regenerate transactions)
- Negative balances: Permit but flag; dues tracked
- Guest attendees: Allow ad-hoc entries; do not impact member balances unless linked
- Rounding issues: Use centralized rounding strategy and optional adjustment transaction
- Duplicate attendance: Enforce unique(member_id, session_id)
- Time overlap: Allow multiple sessions; it’s informational
- Currency: Single currency per deployment
