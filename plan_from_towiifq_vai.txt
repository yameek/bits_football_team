1. Introduction
1.1 Purpose
The Money Collection Tracker is a cross-platform application designed to help teams, groups, and organizations manage financial transactions and collect money from individuals. The system tracks payments, balances, attendance at events, and organizes sessions (practices and matches).

1.2 Document Scope
This SRS document defines all functional and non-functional requirements for the Money Collection Tracker application across web and mobile platforms.

1.3 Overview
The application provides:

Individual management with contact information
Transaction tracking (payments and charges)
Balance calculation and monitoring
Session scheduling (practices and matches)
Attendance tracking
Category management for transactions
Field/location management
Privacy compliance with GDPR-like principles
2. Scope
2.1 System Boundaries
The Money Collection Tracker includes:

Web Application - Full-featured dashboard for desktop users
Mobile Application - Native iOS/Android app via React Native/Expo
Backend API - RESTful API for data operations
Database - PostgreSQL database for persistent storage
2.2 Out of Scope
Payment processing/payment gateway integration
Email notifications
SMS notifications
User authentication (currently single-user per deployment)
Real-time synchronization between devices
Offline mode
3. Functional Requirements
3.1 Individual Management
FR-1.1: Create Individual
Description: Users can add a new individual to the system
Inputs: Name (required), Email (optional), Phone (optional)
Process: Store individual record in database with zero initial balance
Output: Individual record created, list updated
Platforms: Web, Mobile
FR-1.2: View Individual List
Description: Users can view all individuals in the system
Display: Name, email, phone, current balance
Sorting: By name or balance
Filtering: By balance status (positive/negative)
Platforms: Web, Mobile
FR-1.3: View Individual Details
Description: Users can see detailed information about a specific individual
Display: Full contact info, total balance, transaction history
Platforms: Web, Mobile
FR-1.4: Update Individual Information
Description: Users can modify individual's contact details
Editable Fields: Name, Email, Phone
Platforms: Web (via API)
FR-1.5: Delete Individual
Description: Users can permanently delete an individual and all associated data
Cascade Delete: All transactions and attendance records are deleted
Confirmation: System requires explicit confirmation with warning message
Platforms: Web, Mobile
Compliance: Meets App Store Guideline 5.1.1(v)
3.2 Transaction Management
FR-2.1: Create Transaction
Description: Users can record a transaction for an individual
Fields Required:
Individual ID
Amount (positive decimal)
Transaction Type (Payment/Charge)
Description (optional)
Category ID (optional)
Transaction Date

Process:
Validate inputs
Create transaction record
Automatically update individual's total_balance

Platforms: Web, Mobile
FR-2.2: View Transactions
Description: Users can view transaction history
Display: Individual name, amount, type, date, description, category
Sorting: By date (newest first)
Pagination: Show latest 10 transactions on dashboard
Platforms: Web, Mobile
FR-2.3: Transaction Types
Types Supported:
Payment: Money received from individual (increases balance)
Charge: Money owed by individual (decreases balance)

FR-2.4: Balance Calculation
Automatic: System automatically recalculates balance when transactions change
Formula: total_balance = SUM(payments) - SUM(charges)
Real-time: Balance updates immediately upon transaction creation/deletion
3.3 Category Management
FR-3.1: Create Transaction Category
Description: Users can create custom transaction categories

FR-3.2: View Categories
Description: Users can see all transaction categories

Platforms: Web (Management Center)
FR-3.3: Delete Category

5. Data Requirements
5.1 Data Entities
5.1.1 Individuals Table
sql


- id (Primary Key)
- name (VARCHAR 255) - Required
- email (VARCHAR 255) - Optional
- phone (VARCHAR 50) - Optional
- total_balance (DECIMAL 10,2) - Calculated
- created_at (TIMESTAMP)
- updated_at (TIMESTAMP)
5.1.2 Transactions Table
sql


- id (Primary Key)
- individual_id (Foreign Key to Individuals)
- amount (DECIMAL 10,2) - Required
- transaction_type (ENUM: payment, charge) - Required
- description (TEXT) - Optional
- category_id (Foreign Key to Categories) - Optional
- transaction_date (TIMESTAMP) - Required
- created_at (TIMESTAMP)
5.1.3 Categories Table
sql


- id (Primary Key)
- name (VARCHAR 255) - Required
- description (TEXT) - Optional
- color (VARCHAR 7) - Hex color code
- created_at (TIMESTAMP)
- updated_at (TIMESTAMP)
5.1.4 Sessions Table
sql


- id (Primary Key)
- name (VARCHAR 255) - Required
- session_type (ENUM: practice, match) - Required
- field_id (Foreign Key to Fields) - Optional
- scheduled_date (TIMESTAMP) - Required
- description (TEXT) - Optional
- created_at (TIMESTAMP)
- updated_at (TIMESTAMP)
5.1.5 Fields Table
sql


- id (Primary Key)
- name (VARCHAR 255) - Required
- location (VARCHAR 255) - Optional
- google_maps_url (TEXT) - Optional
- latitude (NUMERIC 10,8) - Optional
- longitude (NUMERIC 11,8) - Optional
- created_at (TIMESTAMP)
- updated_at (TIMESTAMP)
5.1.6 Attendance Table
sql


- id (Primary Key)
- session_id (Foreign Key to Sessions)
- individual_id (Foreign Key to Individuals)
- status (ENUM: present, late, absent) - Required
- notes (TEXT) - Optional
- marked_at (TIMESTAMP)
- created_at (TIMESTAMP)
- Unique Constraint: (session_id, individual_id)
5.2 Data Validation
5.2.1 Individual Data
Name: Non-empty string, max 255 characters
Email: Valid email format (optional)
Phone: Valid phone format (optional)
5.2.2 Transaction Data
Amount: Positive decimal, max 10 digits with 2 decimals
Type: Must be 'payment' or 'charge'
Date: Valid timestamp, not in future
5.2.3 Category Data
Name: Non-empty string, max 255 characters
Color: Valid hex color code (#RRGGBB)
5.2.4 Session Data
Name: Non-empty string
Type: Must be 'practice' or 'match'
Date: Valid future timestamp
5.3 Data Retention
Individuals: Permanently stored until deleted
Transactions: Permanently stored until related individual deleted
Attendance: Permanently stored until related session deleted
Categories & Fields: Permanently stored until deleted
Backup: Daily automated backups, retained for 30 days
5.4 Data Privacy
No personal data tracking: App doesn't track user behavior
No third-party sharing: Data is never shared externally
User control: Users can delete all their data
Secure storage: Data encrypted at rest (if deployed with HTTPS)

7. System Architecture
7.1 Technology Stack
Frontend (Web)
Framework: React 18+ with Next.js
State Management: TanStack React Query (data fetching)
State Storage: Zustand (client state)
Styling: Tailwind CSS
UI Components: Lucide React (icons)
Build Tool: Vite
Frontend (Mobile)
Framework: React Native with Expo
Navigation: Expo Router
State Management: TanStack React Query (data fetching)
State Storage: Zustand
UI Components: Lucide React Native (icons)
Platform Support: iOS and Android
Backend
Runtime: Node.js
Framework: Built-in Node.js HTTP (via Next.js API routes)
Database Library: Custom SQL library with template tags
API Style: RESTful
Database
DBMS: PostgreSQL 17+
Schema: Normalized relational schema
ORM: Custom SQL wrapper with parameter binding
7.2 API Architecture
API Design
Style: RESTful
Format: JSON
Authentication: None (single-user deployment)
Rate Limiting: Not implemented
Versioning: Not implemented
API Endpoints
Individuals
GET /api/individuals - List all individuals
POST /api/individuals - Create individual
GET /api/individuals/[id] - Get individual details
PUT /api/individuals/[id] - Update individual
DELETE /api/individuals/[id] - Delete individual (with cascade)
Transactions
GET /api/transactions - List all transactions
POST /api/transactions - Create transaction
GET /api/transactions/[id] - Get transaction details
Categories
GET /api/categories - List all categories
POST /api/categories - Create category
Fields
GET /api/fields - List all fields
POST /api/fields - Create field
Sessions
GET /api/sessions - List all sessions
POST /api/sessions - Create session
Attendance
GET /api/attendance - List attendance records
POST /api/attendance - Mark attendance
